# SoftHertz Tool 开发规范

## 1. 适用范围

本规范适用于：

- `src/soft_hertz_tool` 正式代码；
- `tests` 自动化测试；
- `packaging` 构建入口；
- 启动脚本、CI 和当前项目文档。

协议、线程、生命周期、设备名称和验收边界属于强约束。新代码应与现有模块风格一致。

## 2. 开发流程

非简单功能按以下顺序实施：

1. 在 `docs/development/<feature>/plan.md` 说明背景、目标、非目标、设计、风险和实施步骤；
2. 在同目录建立 `acceptance.md`，把验收项写成可执行命令或可观察结果；
3. 明确受控协议版本、目标硬件、操作系统和未覆盖环境；
4. 获得范围确认后开始实现；
5. 实现期间维护 `development.md`，记录仍然有效的设计决策、测试结果和未闭环项；
6. 完成后逐项对照 plan 与 acceptance review；
7. 更新 README、协议说明、TODO 和验收边界。

简单拼写、注释或无行为变化的机械修改可以不建立专题目录，但仍需执行适当检查。

## 3. 事实与文档优先级

协议相关事实按以下顺序判断：

1. `docs/protocols/controlled-originals` 中明确版本的受控原件；
2. 经确认的补充说明或设备方结论；
3. 当前协议实现与自动化测试；
4. `docs/protocols/readable-notes` 的检索性转写；
5. 抓包、日志和经验推断。

出现冲突时不得猜测。应记录协议版本、字段位置、原始帧和冲突点，再请求确认。Markdown 转写不能替代受控原件。

## 4. 命名规范

- 对外产品名使用 `SoftHertz Tool`；
- Windows 产物使用 `SoftHertz_Tool.exe`；
- Python 包使用 `soft_hertz_tool`；
- 1024 发射阵列使用 `AFDT1024`；
- 1024 接收阵列使用 `AFDR1024`；
- `AFDTR` 只作为工作区名称；
- 内部 `afdtr1024`/`AFDTR1024*` 只表示 TX/RX 共用实现。

设备 key、Workspace key、设置 key 和协议枚举一旦用于持久化或外部接口，应保持稳定；需要修改时提供明确迁移策略和测试。

## 5. Python 代码

- 支持 Python 3.9+；
- 使用 4 空格缩进；
- 建议每行不超过 120 字符；
- 新增公共函数、公共方法和复杂容器使用类型注解；
- 优先使用 `dataclass`、`Enum` 和小型不可变值对象表达协议状态；
- 注释解释“为什么”和协议约束，不逐行复述代码；
- 正式生产模块、类、函数和方法均应有 docstring；简单私有辅助函数可用一句话说明职责；
- 公共或复杂函数的 docstring 应说明关键输入、返回语义、单位或协议约束，以及可能抛出的
  异常或线程/生命周期前置条件；
- 算法、状态机、跨线程信号和兼容迁移应增加解释设计原因的行内注释，不为显而易见的赋值
  重复写注释；
- 用户可见文本和项目注释优先使用中文；
- PySide6 槽函数使用 `@Slot`；
- 捕获异常时保留可诊断上下文，禁止无条件吞掉异常；
- 不在模块导入阶段打开串口、创建窗口或启动线程。

## 6. 架构与依赖

固定依赖方向：

```text
app -> workspaces -> devices -> shared
```

- `shared` 不导入具体设备、工作区或应用；
- `devices` 不导入工作区或应用；
- Workspace 只组合 Panel 和管理生命周期；
- 主窗口只通过 registry 管理 Workspace；
- 设备专用逻辑放入对应 `devices/<device>`；
- 两个设备存在稳定、真实的公共行为时才提取共享抽象；
- 不为减少少量重复而制造跨设备条件分支。

修改模块边界后必须运行依赖边界测试。

## 7. 协议模块

`protocol.py` 应保持确定性和无副作用：

- 明确帧头、长度、命令、地址、端序和校验覆盖范围；
- 明确缩放、偏移、符号、量化和物理单位；
- 构帧函数校验输入范围，非法输入抛出具体异常；
- 解析函数检查长度、帧头和校验后再访问字段；
- 返回语义字段，不把不透明下标传播到 UI；
- 不导入 Qt 控件、pyserial 或具体 Panel；
- 不使用全局可变协议状态。

协议变更至少同步：

- protocol；
- stream；
- Driver 的事件分派；
- simulator；
- 正常与异常测试向量；
- 协议说明和 README 功能边界。

AFDT1024/AFDR1024 的波束字段、频率量化和 TX/RX 地址不得混用。任何调整先核对对应设备与协议版本。

## 8. 流式拆帧

`stream.py` 必须支持串口实际输入形态：

- 单帧被拆成多个字节块；
- 多帧粘在一个字节块；
- 帧前存在垃圾字节；
- 坏长度；
- 坏校验；
- 半个帧头留在缓冲区末尾；
- 错误帧后继续恢复下一帧。

拆帧器应输出完整帧或带原因的丢弃事件。不得因一个坏帧清空所有可能有效的后续数据。

## 9. Driver 与串口

- Driver 对 UI 提供语义方法，例如 `query_status()`，而不是要求 UI 传入裸帧；
- Driver 负责调用 protocol 构帧、向发送队列提交数据、接收 stream 事件并发布语义状态；
- 每个 Driver 独占自己的串口会话；
- pyserial 对象只能在所属线程打开、读写和关闭；
- 发送队列必须有界，队列满时返回失败并生成可诊断事件；
- 串口读写必须有有限超时；
- 停止路径必须可重复调用，并返回线程是否真正退出；
- 快速重连使用连接代际过滤旧信号；
- 任何原始 TX/RX/DROP 都进入 `FrameRecord`。
- `FrameRecord.model` 使用公开硬件型号；`port` 使用串口名或稳定的可读连接标签，不新增
  `endpoint` 等平行字段。

禁止在 UI 线程直接执行 `serial.read()`、`serial.write()`、`close()` 或阻塞等待。

## 10. Panel 与 Workspace

Panel：

- 只负责输入校验、触发 Driver 语义方法和显示状态；
- 不手工拼帧、计算校验或维护流式接收缓冲；
- Qt 控件只能在主线程修改；
- 高频数据使用缓存、批处理或定时刷新；
- 断开按钮、工作区切换和窗口退出复用同一停止路径；
- 串口错误、超时和协议拒绝应对操作员可见。

Workspace：

- 组合一个或多个 Panel；
- 实现幂等 `activate()`、`deactivate()` 和 `shutdown()`；
- 隐藏时暂停非必要定时器；
- `deactivate()` 在任一设备未安全停止时返回失败；
- 将各设备的 `frame_signal` 汇总给主窗口。

## 11. 高频数据与日志

- 原始接收速率不等于 UI 刷新速率；
- AFD01_QS A0 可约 100 Hz 接收，业务 UI 不高于 10 Hz；
- 全局报文区按批次刷新并限制最大行数；
- 日志由独立线程写入；
- 日志默认按 50 MiB 单文件轮转；
- 不在串口线程进行大文本格式化、文件选择或耗时导出；
- 日志不得包含口令、令牌和与调试无关的敏感数据。

增加新的报文类型时继续使用 `FrameRecord`，不要建立不兼容的第二套监视器。

## 12. 模拟器

- 模拟器导入正式 protocol/stream；
- 设置命令尽量形成“设置后查询”的闭环；
- 正确模拟广播不回复、目标 ID 回复和超时；
- 可配置端口、波特率和必要的设备 ID；
- 高频上报按绝对截止时间调度，阻塞后跳过错过周期，不突发补帧；
- 模拟器专用便捷逻辑不得成为协议真值。

模拟器测试只能证明主机协议链路，不证明真实硬件电气、时序或固件行为。

## 13. 自动化测试

测试按职责放置：

- `tests/devices`：协议、流解析、Driver、Panel、模型、控件和模拟器；
- `tests/shared`：传输、日志、报文监视和共享 UI；
- `tests/integration`：registry、工作区生命周期、配置、依赖边界和仓库结构。

缺陷修复先增加可复现测试。协议测试至少包含：

- 权威正常向量；
- 上下限和非法输入；
- 坏长度和坏校验；
- 分包、粘包和垃圾字节；
- 设置/查询回读闭环；
- TX/RX 或设备变体差异。

提交前最低检查：

```bash
QT_QPA_PLATFORM=offscreen python -m pytest -q
python -m compileall -q src tests packaging
git diff --check
```

测试通过后仍需按风险完成目标平台和真实设备验收。

## 14. 资源、设置与打包

- 图片和图标放入 `src/soft_hertz_tool/resources`；
- 通过包内资源定位加载，不使用依赖当前工作目录的相对路径；
- 新资源同步加入 `pyproject.toml` package data 和打包检查；
- 非敏感偏好使用当前 QSettings 产品命名空间；
- 用户日志和导出文件写到用户目录，不写源码目录；
- PyInstaller 从 `packaging/entrypoint.py` 进入；
- 构建输出只进入 `build/`、`dist/` 等忽略目录。
- 当前 `0.0.0` 是开发包版本；在 tag、包元数据、EXE 文件版本和 Release 由单一来源生成并校验前，
  不得把任一 tag 自动视为可发布版本。

Windows EXE 必须在 Windows 上构建和验证。其他平台的 PyInstaller 成功不能证明 Windows 产物可用。

## 15. 文档

- README 只描述当前功能、架构、运行方式、规范、TODO 和验收边界；
- 临时排障过程和逐条提交清单不进入长期项目文档；
- 临时分析结束后，应将有效结论收敛到当前文档并删除失效细节；
- 协议原件放 `controlled-originals`，便于检索的说明放 `readable-notes`；
- 代码行为、命令和路径变化时同步更新文档；
- 未完成的 Windows、硬件、性能或协议确认必须明确保留。

## 16. Git、生成物与安全

- 不主动提交，除非维护者明确要求；
- 提交使用 `type(scope): 中文描述`；
- 保留工作区中与当前任务无关的修改；
- 不提交 `.venv`、缓存、日志、`build/`、`dist/`、`.spec`、EXE 或 ZIP；
- 不执行无明确范围的破坏性清理；
- 不把口令、Token、私钥、客户数据或本机绝对路径写入仓库；
- 发布前检查 Artifact、Release 资产和 SHA256，而不只看 CI job 状态。

## 17. 完成定义

功能只有同时满足以下条件才可标记完成：

- 实现符合 plan 的范围和非目标；
- acceptance 中的软件检查已执行并记录；
- 受影响的协议、模拟器、测试和文档已同步；
- 没有引入反向依赖、阻塞 UI 或无法停止的线程；
- 操作员能看到错误和超时；
- 对应平台/硬件未验证项仍明确标记为未完成；
- README 与 TODO 反映当前事实。
